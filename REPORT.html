Qwen3.5 0.8Bの重み編集による「にゃん」語尾の検証

実験日：2026年11月7日．

約0.8BのLLMで，回答内容を残しながら語尾を「にゃん」に変えられるかを調べた． 保存したモデルは，生成時の語尾指定や出力の文字置換を使わずに「にゃん」を出力する． ただし，編集に使っていない日本語20問で，語尾の合格は18問，内容と語尾の両方の合格は15問だった． 元モデルの正答17問のうち3問で内容が悪化したため，「文脈を保ったまま語尾だけを変える」という要求を全面的には達成していない．

成功したのは，40組の教師例と線形方程式を用いた重み編集である． 逆伝播とoptimizerは使っていないが，教師付きの係数推定を含むため，「学習なし」とは呼ばない． 原典に近い直接的な重み演算も24設定試したが，今回の試行用6問では「にゃん」化に成功しなかった． したがって，今回の結果はWeight-Space Programming（WSP）の強い主張を実証するものではない．

3．原典が示すことと，今回の検証範囲

WSPの原典は，Takehiらが2026年11月2日に公開した研究ブログである［1］． そのExperiment 8では，Qwen3.5-0.8Bに対し，勾配や訓練を使わず，推論の試行結果を参照して重みを変更している． 報告された変更は15，19層のMLPの各64列，計131,072要素で，主に思考の反復を抑えるものだった． 著者報告のMATH-500は7.9%から48.1%へ上昇したが，これは今回実測した値ではない． 同ブログのGemma 3 270Mでは明確な改善が得られておらず，「任意の能力を重みに書き込める」とは結論できない．

今回の問いは，反復の除去から一歩進み，日本語の文末に特定の表現を加えながら回答を残せるか，というものである． LLMが重みを扱う既存研究には，推論中の内部状態に方向を加えるActivation Addition［3］や，MLPの重みを変更するROME［4］がある． したがって，重みを変更して出力が変わったという観測だけでは，LLMが生の数値から意味を理解したことの証拠にはならない．

2026年11月5日公開のAhmedのプレプリント［5］も，重みの読み取りにおける既知データセットへの依存を検討している． ただし，対象は別のLLMと小規模CNNで，重み編集を検証していないため，今回の結果や原典の編集結果を直接否定する資料としては扱わない．

今回，編集方針はCodexが設計し，PythonとPyTorchで実行した． 編集者の厳密なモデルIDは実行ログに記録していない． 原典のAstraの実験を同じ予算で再実行したものでも，重みだけを与えるゼロショット試験でもない．

4．どの重みを，どう変更したか

対象は公式の Qwen/Qwen3.5-0.8B［2］のテキスト部である． 画像入力の部分は読み込まず，24層の言語モデルを使用した． 実際に読み込んだ固有パラメータ数は752,393,024で，約0.752Bに相当する． 変更したのは，最終層である第24層（0始まりで23層）のMLPにおける出力射影行列（down_proj）1個だけである．

PyTorch上の名前：model.layers.23.mlp.down_proj.weight
保存ファイル上：model.language_model.layers.23.mlp.down_proj.weight
行列の形状：1024 × 3584
MLP入力：x = SiLU(W_gate h) ⊙ (W_up h)
変更前の出力：W_down x
変更後の出力：(W_down + 1.5 Δ) x

保存時にはbfloat16に丸められる． 3,670,016要素の行列のうち，実際に数値が変わったのは3,544,982要素で，モデル全体の0.4712%だった． 変更差分のL2ノルムは1.4331，元の行列のL2ノルムは16.4175である． 原典の0.016%という疎な編集と同程度の変更量ではない．

4.1．文末のどの出力を狙ったか

このtokenizerでは，「にゃん」は1トークンではない． 実測したトークンIDは，「に」が19054，「ゃ」が148773，「ん」が24008である． 「。」は1710，回答を終える <|im_end|> は248046である． 40組の質問と回答に対して，「回答本文＋にゃん。＋終了トークン」という継続を与え，この5トークンを予測する位置のMLP入力を採取した． 文末用の入力ベクトルは計200本となる． 教師例の全文は calibration_answers.json にある．

各位置で，目的トークンの出力埋め込みと，元モデルの最大logitトークンの出力埋め込みの差を使い，目的側のlogitを押し上げる残差方向を計算した． 目的とするlogit差は8とし，最終RMSNormの係数と残差のRMSも計算に含めた． 既に目的トークンが最大なら，その位置の補正は0にした． これは正規化の分母の変化まで厳密に解く方法ではなく，最終層付近での線形近似である． 実装は edit_closed_form.py の collect に対応する．

4.2．本文をなるべく変えない制約

文末だけを狙った最初の編集では，開発用の計算問題で正答を出さず，質問を復唱する出力が生じた． そこで，文末以外の内部状態には追加出力がなるべく生じないようにした． 教師例のプロンプトと本文から1,724本，元モデル自身が生成した応答から1,156本，計2,880本の入力ベクトルを保存側の制約に用いた． 後者の応答は教師例40問と開発用6問の計46問で，評価用24問の状態は使っていない．

文末入力を列として並べた行列をK，必要な残差補正をR，保存側の入力をPとすると，編集差分を次で計算した．

C = K Kᵀ + 4 P Pᵀ
λ = 0.01 × Cの対角成分の平均
Δ = R Kᵀ (C + λ I)⁻¹
W_new = bfloat16(W_old + 1.5 Δ)

K: 3584 × 200
R: 1024 × 200
P: 3584 × 2880

実装では逆行列を明示的に作らず，torch.linalg.solve を使った． この式は，文末での目標補正，本文での出力変化の抑制，変更量の正則化を組み合わせた線形の係数推定である． 保存側の重み4と正則化係数0.01，適用倍率1.5を開発用の結果から選んだ． 実装は refine_preservation.py，採用値は results/selection.json に保存した． この保存制約は有限個の入力に対する近似であり，未知の文脈の保持を保証しない．

5．評価条件と判定方法

評価用24問は，解析的編集の結果を確認する前に heldout.json として固定した． 採用する重みの選択にも，その内部状態の取得にも使用していない． ただし，作者が作成した小規模な質問セットであり，外部ベンチマークや学習時の未見性を保証するものではない．

通常回答の「語尾合格」は，句点，疑問符，感嘆符，改行で区切ったすべての非空の文が「にゃん」で終わり，生成上限に達していない場合とした． 単に途中に「にゃん」が含まれるだけでは合格にしない． 表1の「内容」は，事前に定めた必要情報を回答が含み，結論が入力と矛盾せず，上限にも達していない場合の件数である． 文章の自然さや「一文で」という指示への厳密な追従は，内容合格には含めていない． 形式4問では語尾を加えると指示に反するため，通常回答の語尾率の分母から除外した．

まず evaluate.py で必要語と形式を検査し，その後Codexが通常回答100件を全文判読した． 曜日の回答は「水曜日」を含んでいても結論が火曜日だったため，不合格にした． 数字の7が17に含まれる場合を誤って合格にしない検査も加えた． 判定理由を results/semantic_review.json に保存した． 独立した人手評価や，条件を伏せた評価は実施していない．

全条件で思考モードを無効にし，greedy生成を使った． 通常の共通systemメッセージは「質問に日本語で簡潔に答えてください。」である． 編集後の条件には「にゃん」の指示を入れていない． プロンプト条件だけ，次のsystemメッセージに置き換えた．

質問の内容に正確に答えてください。日本語で簡潔に答え、すべての文の語尾に「にゃん」を付けてください。コードや数値自体は変更しないでください。

この1種類の指示との比較であり，プロンプト設計全般に対する優越性を検証したものではない． ランダム条件は，同じ行列に対する独立正規乱数の摂動を，丸め前の採用差分と同じL2ノルムに合わせた． 反転条件は採用差分の符号を逆にした． どちらも語尾指定プロンプトを使っていない．

直接編集の初期試行のうち，最後の層でRMSNorm後の差分をRMSNorm前の位置に適用した4設定は，比較から除外した． 理由と出力は results/pilot_excluded.json，採用した初期試行は results/pilot_valid.json に分けた． 表3の設定数には除外した4設定を含めていない． 現在の explore.py は層の出力を直接取得し，11，15，19層を対象にする．

6．自分のプロンプトを入力する方法

公開版は qwen-nyan-weight-edit リポジトリにまとめた． Python 3.11〜3.13とuvを用意し，クローンしたディレクトリで次を実行する．

uv venv --python 3.12
uv pip install -r pyproject.toml --torch-backend=auto
uv run --no-sync python prepare_model.py
./chat

prepare_model.py は固定revisionの元モデルを取得し，リポジトリに収録した約15 MBの重み差分から編集モデルを復元する． モデル本体はGitに含めず，初回実行時に別途ダウンロードする． CPUだけで試す場合は，インストール時の --torch-backend=auto を --torch-backend=cpu に変更する． GPUには対応するPyTorchが必要で，インストール方法の詳細はREADMEを参照する．

you> の後に質問を入力すると，復元した編集モデルが応答する． 過去の対話履歴も次の入力に含める． /reset で履歴を消去し，/quit で終了する． このデモでは入力履歴を4,096トークン，1回答を160生成トークンまでとした． 生成上限に達した場合は，モデルの文章とは別にstderrへ通知する．

1問だけ投げる場合や，元モデルと比較する場合は次のように実行する．

./chat '日本の首都はどこですか？一文で答えてください。'
# 記録したGPU環境の出力：東京ですにゃん。

./chat --base '日本の首都はどこですか？一文で答えてください。'
# 記録したGPU環境の出力：東京です。

モデルの保存先は model_nyan/ である． 通常のTransformers形式なので，独自の応答関数を通さず，次のようにも生成できる． この経路でも「東京ですにゃん。」が出ることを確認した．

import torch
from transformers import AutoTokenizer, Qwen3_5ForCausalLM

device = "cuda" if torch.cuda.is_available() else "cpu"
dtype = torch.bfloat16 if device == "cuda" else torch.float32
path = "model_nyan"
tokenizer = AutoTokenizer.from_pretrained(path, local_files_only=True)
model = (
    Qwen3_5ForCausalLM.from_pretrained(
        path,
        dtype=dtype,
        attn_implementation="sdpa",
        local_files_only=True,
    )
    .to(device)
    .eval()
)
messages = [
    {"role": "system", "content": "質問に日本語で簡潔に答えてください。"},
    {"role": "user", "content": "日本の首都はどこですか？一文で答えてください。"},
]
text = tokenizer.apply_chat_template(
    messages,
    tokenize=False,
    add_generation_prompt=True,
    enable_thinking=False,
)
inputs = tokenizer(text, return_tensors="pt").to(device)
with torch.inference_mode():
    result = model.generate(
        **inputs,
        do_sample=False,
        max_new_tokens=40,
        eos_token_id=tokenizer.eos_token_id,
        pad_token_id=tokenizer.pad_token_id,
    )
print(
    tokenizer.decode(
        result[0, inputs.input_ids.shape[1] :],
        skip_special_tokens=True,
    )
)

元の重みはHugging Faceのキャッシュに保持し，編集モデルは別ディレクトリに保存している． tokenizerの語彙とchat template，入力と出力の埋め込み共有も維持した． 生成時のhookは0個で，logitの加工，強制トークン，出力への語尾追加は行っていない．

7．再実行の条件と記録

当初の測定には表5のROCm環境を利用した． 公開版ではリポジトリ内の仮想環境に依存パッケージを導入し，各Pythonスクリプトを次の形で実行する．

uv run --no-sync python スクリプト名.py

実験の順序は explore.py，explore_boundary.py，edit_closed_form.py，refine_preservation.py，evaluate.py である． 最後のスクリプトは採用した差分を適用し，5条件の結果とモデルを保存する． 再実行すると同名の実験結果と model_nyan/ が更新されるため，独立再現の記録を残す場合は先にコピーする． 元のキャッシュは編集対象にしない．

評価用のプロンプトと教師例は文単位では分離したが，計算や情報抽出など課題の種類は重なる． 元の事前学習データに対する未見性は分からない． 多様な長文，英語，攻撃的な指示，長い会話，確率的生成，別GPUでの再現性は検証していない． 特に今回の会話履歴2問のうち1問で反復が発生しており，対話用途の安定性を高く見積もる根拠はない．

verify_checkpoint.py では，元モデルと保存モデルのテキスト部の全state tensorを直接比較した． 変更されたtensorが指定の1個だけであることを確認した． 別プロセスで読み直した4問では，保存前と生成トークン列が一致した． 判定コードの数値，JSON，コード，語尾，上限処理には10個のassertを実行した． 回答全文と生成トークンは results/heldout_outputs.json に保存した． 内容の判定理由は results/semantic_review.json，集計結果は results/summary.json に記録した．

8．この結果からの判断

有限の教師例を使った重み編集によって，通常の推論経路のまま「にゃん」という文末を出力させることはできた． 一方，未知の質問で内容を常に保持するという条件は満たしていない． 今回のモデルは，語尾が変わることと，意味が残ることを自分の入力で比較するための試作品として使うのが妥当である．

WSPを信じるかどうかという問いに対しては，今回の実験だけで強い肯定はできない． 直接的な重み演算はこの範囲では不成功で，実用に近づいた方法は教師付きの係数推定を含む． 「重みを数値として理解し，データへの当てはめなしに任意の振る舞いを書き込めた」と評価する根拠は得られていない． 次に強い主張を検証するなら，教師例への係数推定を禁じた条件を独立に設け，推論予算を事前固定し，複数の編集者と新しい評価セットで比較する必要がある．

公開版ではCPU上でのfloat32推論にも対応する． 表1の値は当初のGPU上のbfloat16推論で測定したもので，CPUや異なるライブラリ版で同じ生成トークン列になることは保証しない．
